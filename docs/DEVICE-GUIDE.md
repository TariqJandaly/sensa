# Linking a device to the server

This is the operator's guide: creating a device in the web app, pairing
people to it, what the watch must publish, and how to test everything before
the hardware exists. If you want the Python side of the watch itself, that
is [PI-WIRING.md](PI-WIRING.md).

## Before anything runs

Three processes need to be up. Postgres and Mosquitto come from the repo
root, the rest from their app folders:

```bash
# once: infrastructure
docker compose up -d

# terminal 1: the website
cd apps/web
bunx vite dev --port 3123 --host

# terminal 2: the MQTT bridge (forwards device traffic to the API)
cd apps/ingest
DEVICE_TOKENS_FILE=/path/to/tokens.json \
  SENSAA_API_URL=http://localhost:3123 \
  bun run start

# terminal 3: the simulator, only while testing without hardware
cd apps/device-sim
bun run start --device <deviceId> --token <deviceToken> --interval 2000
```

The bridge needs a token map: a small JSON file (or the `DEVICE_TOKENS`
environment variable) mapping device ids to tokens. You get both values
when you provision the device in the app. Example:

```json
{
  "15e3aa3f-ee86-4ad8-b84d-dd0ab56b94ef": "A43f...long-token-here"
}
```

Keep this file outside the repo. Treat device tokens like passwords.

## Creating a device in the app

1. Create an account at `http://localhost:3123`. The first thing you will
   see on the dashboard is an honest empty state: no device yet.
2. Open the setup page (ربط الجهاز in the bottom bar).
3. Two options:
   - Create a real device: type its name (for example سارة) and save.
   - Create a demo device: one button, no name needed. A demo device is
     flagged `isDemo`, which is what makes the demo badge appear on the
     dashboard and keeps test data honestly labeled.
4. The page then shows two things, once:
   - the pairing code, `XXXX-XXXX`, which family members will type to
     follow the wearer
   - the device token, a long random string, which goes into the watch
     config (or into the simulator command for a demo device)

Copy the token right away. It is never shown again, and it cannot be
recovered, only regenerated by creating a new device. The setup page also
prints the exact simulator command for demo devices, ready to copy.

## Pairing people

Two ways, both verified working:

- A family member creates their own account, opens the setup page, types
  the pairing code, and joins as a caregiver. They immediately see the
  device on their dashboard and receive alerts if their notify switch is
  on.
- The wearer (or any existing member) opens the caregivers page (من
  يرافقك), types the caregiver's email, and adds them. The person must
  already have an account with that email.

Roles are simple: whoever created the device is the wearer and cannot be
removed. Everyone else is a caregiver and can have notifications toggled
per person. Removing a caregiver is one tap, and it removes their access
and their alerts at the same time.

## What the device must publish

Three topics, all QoS 1. Field names are validated, not parsed generously:
anything off-spec is dropped by the bridge with a log line telling you
exactly which field failed.

### Readings, batched

Topic: `sensa/<deviceId>/readings`

```json
{
  "deviceId": "15e3aa3f-ee86-4ad8-b84d-dd0ab56b94ef",
  "readings": [
    {
      "capturedAt": "2026-11-23T17:15:00Z",
      "hrBpm": 74.2,
      "spo2Pct": 97.1,
      "tempC": 36.61,
      "gsrOhm": 238400,
      "accelX": 0.05,
      "accelY": 0.02,
      "accelZ": 9.81,
      "status": "SAFE",
      "flags": []
    }
  ]
}
```

Rules that matter:

- 1 to 1000 readings per batch. The watch should batch small (6 is plenty)
  and flush every 30 seconds or so.
- `capturedAt` is the reading's own time, ISO 8601 with the timezone, taken
  when the sensors were read, not when the batch went out. This is what
  makes offline buffering truthful.
- `hrBpm`, `spo2Pct`, `tempC`, `gsrOhm`, `accelX`, `accelY`, `accelZ` are
  all optional (nullable) so a dead sensor does not kill the batch.
- `status` is SAFE, WATCH or ALERT, and `flags` is a list of short reason
  strings. The server re-evaluates anyway, so if in doubt send the raw
  numbers and `SAFE`; the thresholds saved in the settings page decide.

### SOS, the emergency button

Topic: `sensa/<deviceId>/sos`

```json
{ "capturedAt": "2026-11-23T17:16:40Z", "lat": 21.5433, "lng": 39.1728 }
```

Never deduplicated, never rate limited away. The server creates the event
and pushes to everyone immediately, and the alerts page shows the
coordinates with a link that opens them on a map.

### Heartbeat

Topic: `sensa/<deviceId>/heartbeat`

```json
{ "ts": "2026-11-23T17:16:41Z", "batteryPct": 63 }
```

Send one every 30 seconds while the watch runs. Two things depend on it:
the ONLINE/OFFLINE state (no heartbeat for 90 seconds flips the device
OFFLINE and records the moment the feed went quiet) and the battery display.

## Testing without the hardware

1. Create a demo device as above and copy the printed simulator command.
2. Run the three processes from the top of this document.
3. Watch the dashboard: within a minute you should see the status hero
   turn from no-reading to a fresh reading line (آخر قراءة قبل بضع
   ثوان), the device go ONLINE with a battery, and the chart fill up.
4. Let the simulator run. Around minute 5 of its cycle the heart rate
   climbs, SpO2 drops, the reading statuses go WATCH then ALERT, and an
   ALERT event appears with a push notification if you subscribed.
5. The SOS phase publishes one emergency with coordinates. Check the
   alerts page: the row shows the coordinates with a map link and a
   "بانتظار الرد" chip until someone taps acknowledge.

You can also drive the ingest API directly with curl, which is handy when
you want to test exactly one threshold:

```bash
NOW=$(date -u +%Y-%m-%dT%H:%M:%SZ)
curl -X POST http://localhost:3123/api/ingest/readings \
  -H 'content-type: application/json' \
  -H "x-sensa-device-token: $TOKEN" \
  -d "{\"deviceId\":\"$DEVICE_ID\",\"readings\":[{\"capturedAt\":\"$NOW\",\"hrBpm\":128,\"spo2Pct\":88,\"tempC\":38.6,\"gsrOhm\":400000,\"status\":\"ALERT\",\"flags\":[]}]}"
```

The response tells you whether an alert was raised:
`{"accepted":1,"alertsRaised":1}`. Send the same thing again within five
minutes and you get `alertsRaised:0`: the cooldown dedup doing its job.

## Troubleshooting

**The device stays OFFLINE.** The OFFLINE state is driven by heartbeats
only. Readings alone flip it ONLINE too (they update lastSeen), so if it
stays grey the traffic is not reaching the API. Check the bridge terminal:
every valid batch prints a line. No lines means the broker is unreachable
or the topic is misspelled. Lines but no data in the app means the token map
is wrong: the bridge prints `no token for device ...` when it cannot find
one.

**Readings arrive but no alert fires.** Open settings and check the saved
thresholds: 37.8, 50 to 120, 92, 0.15, 2.5 are the defaults, and the server
evaluates against them. Also check the cooldown: within five minutes of a
previous alert, a new ALERT reading will not create a second event.

**Push never arrives on the phone.** Three common causes, in order of
likelihood: notifications were never enabled for that person (settings,
enable notifications), the phone is on iOS and the site was not added to
the home screen first, or the site is not on HTTPS (localhost works, LAN
IPs do not always, depending on the browser). The server log line
`[push] delivered to user ...` tells you the send itself succeeded, which
narrows it to the phone side.

**A batch is rejected.** The bridge log names the first failing field. The
most common mistakes: `capturedAt` without a timezone, field names copied
from the old JSONL log (`heart_rate_bpm` instead of `hrBpm`), or more than
1000 readings in one batch.

## Security notes for the real deployment

The dev broker accepts anonymous connections because it sits on the lab
machine. Before the real watch goes anywhere near the internet:

- Give the broker per-device usernames and passwords, or client
  certificates, and switch the bridge to them.
- Run Mosquitto with TLS on 8883 and point the watch at it.
- Put the web app behind HTTPS with a real domain, add that origin to
  `TRUSTED_ORIGINS`, and regenerate the Better Auth secret and the VAPID
  keys for production.

The device token is a bearer credential: anyone holding it can publish as
that device. It is never printed in any log, and the stored form is a
hash, so a leaked database does not leak tokens.
